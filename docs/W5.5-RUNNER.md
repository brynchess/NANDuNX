# W5.5 — Windows runner work disk

## Change plan, 2026-10-05

Server `192.168.0.14` has one 100 GiB QEMU SATA disk with an MBR layout. Before this change it had partition 1 (100 MiB system), partition 2 (`C:`, about 79 GiB), partition 3 (850 MiB recovery), and about 20 GiB of unallocated space after it. `C:` could not be expanded without moving the recovery partition. Drive letter `D:` was available.

1. Reconfirm disk number and size, the three existing partitions, at least 19 GiB of unallocated space at the end, and no `D:` volume.
2. Create only a new MBR volume in the unallocated area, assign `D:`, and format it as NTFS with label `NANDuBuild`.
3. Verify that existing partition offsets, sizes, and letters are unchanged.
4. Set runner `host.workdir_parent` to `D:/gitea-work`, restart the runner, and check its Gitea registration.

## Limits and recovery

This changes the test machine's system disk, not a NAND device. It does not move the operating system or existing data, change the recovery partition, or extend `C:`. The runner account must have partition-creation rights; do not substitute another tool that rewrites the existing layout if this gate fails.

If formatting fails, leave the new partition in place, report its state, and format it only after diagnosis. If the new work directory fails, restore the prior `run.cmd` and restart the scheduled task. Removing `D:` requires stopping the runner and checking that no needed artifacts remain; removal is not automatic recovery.

## Result

A 20 GiB logical `D:` volume was created inside a new extended MBR partition at the disk's end. Windows preserved offsets and sizes of partitions 1–3. The new volume is NTFS with label `NANDuBuild`.

At that time, task `NANDu-W1-Gitea-Runner` started at system boot, retried failures every minute up to 999 times, and had no execution timeout. The runner used `C:/Users/nandu-build/gitea-runner/config.yaml`, pointing work to `D:/gitea-work` and cache to `D:/gitea-cache`. The previous startup script was kept as `run.cmd.before-build-disk`.

A forced-termination test showed that scheduled-task retry alone did not restart the runner. Therefore `run.cmd` loops `gitea-runner.exe` and waits 60 seconds after exit. With no active job, runner PID 924 was terminated; PID 420 started a minute later and registered with Gitea. The boot trigger still protects reboot startup; the server was not rebooted.

Job 13 was picked up after moving the work directory. During compilation it worked under `D:/gitea-work` and `C:` retained about 16.35 GiB free. After cleanup, `D:` had about 19.93 GiB free. The workflow result could not be read through the Gitea API because it returned HTTP 401.

## Runner replacement, 2026-10-07

The repository-bound runner was replaced with the instance-level runner `windows-server-2022`. It runs from `C:/Users/nandu-build/gitea-runner-nandunx`, is started at boot by task `NANDuNX-Gitea-Runner`, and advertises the `nandunx-release-windows:host` label. The runner retains the existing `D:/gitea-work` and `D:/gitea-cache` settings.

The old task was unregistered, its process stopped, and `C:/Users/nandu-build/gitea-runner` (including its local registration state) was removed. Gitea Runner 2.3.0 has no local `unregister` command, so its now-offline historical entry may still appear in the Gitea administration UI; remove that stale entry there if the server does not clean it up automatically.
